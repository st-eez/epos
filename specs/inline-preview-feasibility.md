# Inline preview feasibility (palette input method)

2026-07-30 research record: can Epos show live provisional text inside the
focused field, the way native dictation does, without weakening the
one-guarded-write insertion contract? Verdict: **achievable with conditions —
a specific mechanism was overlooked in May — pending one falsifying probe.**

## What was actually tried before

- 2026-05-28 (`c756ea4`..`11bce38`, ~3.5 hours): an InputMethodKit target with
  a real `setMarkedText` streaming implementation (`0973fa2`). Removed the same
  day because a **keyboard-type** input method must be selected as the user's
  keyboard, routing all typing through Epos. That reasoning was correct for the
  type that was built. No technical marked-text failure was ever observed.
- The app never called `TISSelectInputSource`; only the smoke-test install
  script did. Programmatic selection was never product-tested.
- 2026-07-29 (`44118a9`): progressive keystroke insertion retired for real
  revision races and append-only opaque targets. That retirement stands and is
  not revisited here.

## The overlooked mechanism

Apple Dictation (`/System/Library/Input Methods/DictationIM.app`) is an
InputMethodKit input method of type **`palette`** with
`ComponentInvisibleInSystemUI = true`, linking public IMK, with **no
entitlements**. Palette input sources are additive: selecting one does not
replace the keyboard layout (verified live — `com.apple.PressAndHold` is
selected alongside `com.apple.keylayout.ABC`; `TextInputSources.h:963` states
selection of a palette source "has no effect on other input sources").
`IMKInputSession.h:277` explicitly blesses palette input methods sending text
"not generated by user keyboard input". The May attempt's plist simply lacked
`InputMethodType: palette` — a two-key difference from Apple's bundle.

No shipping third-party dictation app uses IMK at all (all use paste or
synthesized keystrokes with their own overlay), so there is **no third-party
precedent for a palette IME** — that absence is the honest risk.

## Closed alternatives

- AX span replacement: Chromium/Electron accept the selection write and
  silently drop the text write (`browser_accessibility_cocoa.mm:3191`,
  `render_accessibility_impl.cc:405`); WebKit's `setSelectedText` is an empty
  body. Settability reporting lies, so support cannot be pre-detected, and a
  failed attempt leaves the selection moved — worse than doing nothing.
- TSM document access: not implemented for arm64; document IDs are
  process-local. `CGEventKeyboardSetUnicodeString` cannot express marked text.

## Probe (pre-registered)

Throwaway palette IME bundle outside the product tree: hardcoded trigger →
`TISEnableInputSource` + `TISSelectInputSource` on itself → `setMarkedText`
growing string for 3 s → `insertText` commit → deselect. Install requires one
logout/login (DevForums 775526). Targets in order: cmux, Ghostty, VS Code,
Slack, TextEdit, Safari field. Record: preedit renders; survives held fn
(Ghostty #4634: preedit dies on modifier — Epos is fn-hold by construction);
commit lands once; behavior on focus change; `unmarkText` commit-vs-discard.

**Kill criterion, decided in advance: if preedit fails in both cmux and
Ghostty, close this line of work.** App-dependent preview in only the easy
apps is worse than today's uniform HUD.

## Design constraint if the probe passes

Marked text is **preview only**. It is discarded before finalization; the
authoritative commit remains `FinalTranscriptInsertionSession`'s single guarded
write. Uncommitted marked text is not in the document, so crash, focus change,
or guard refusal leaves the field byte-identical to fn-press — the
never-corrupt guarantee is unchanged and the input method is purely additive.

## Accepted UX costs

Second signed bundle in `~/Library/Input Methods`; one logout on first
install; no live preview in Secure Input contexts (final write still works);
uninstall needs the documented input-source purge; no Mac App Store (already
forgone).
